Introduction

Topten Simple Theme Options registers a Theme Settings WordPress admin experience: nested sidebar, SPA-style section switching, one options form, responsive controls, composite fields (Tabs, Accordion, Group), conditional required visibility, header quick search, post/taxonomy metaboxes, and optional WooCommerce Product data tabs for per-product fields.

This guide is for developers, agencies, and product teams who ship client sites or bundle STO in a commercial theme. Samples use the SimpleThemeOptions\ namespace and text domain 'simple-theme-options'. It focuses on your sidebar and field PHP under includes/Admin/Sample/; core plugin bootstrap is documented in README.md.

License & resale

GPL v2 or later applies to this plugin’s PHP. When you resell or bundle, include license terms for your layer (theme, config UI, support). Keep GPL headers in shipped PHP. Point customers to this file and to README.md for integration depth.

  • White-label: Replace Sample\ menu and sections with your brand; adjust menu title and icon in Menu::register().
  • Post editor metabox: Optional 'metabox' / 'enable_metabox' on Options\Menu::register(); per-post meta _sto_theme_settings_post saves on Publish / Update (no separate save button). Filter sto_theme_settings_metabox_ui_enabled to hide metaboxes site-wide.
  • WooCommerce Product data tab: Optional per-product STO fields inside the native Product data box on Products → Edit product (saved to _sto_theme_settings_post). Your theme wires the tab; merchants only fill fields and click Update (§2.1d). Do not enable both metabox and woocommerce_product_data on the same menu for product.
  • Support scope: In your own README, separate “STO core behaviour” from “your custom field classes” so buyers know what you maintain.

Requirements

  • WordPress 5.8+
  • PHP 7.4+
  • manage_options for Theme Settings
  • WooCommerce Product data (optional): active WooCommerce; theme adds a Product data tab (§2.1d)

Quick start

  1. Activate the plugin.
  2. Add or change sidebar rows in includes/Admin/Sample/Sections.php so each screen you need exists as a leaf slug (§2).
  3. Add includes/Admin/Sample/Fields/{Name}/{Name}.php (PascalCase folder + filename = class name). In init(), call field APIs then Foo::instance()->register() / register_many() with 'section_slug' equal to that leaf (§1.1 PHP, §6.0).
  4. Optional: rename the Theme Settings menu in includes/Admin/Sample/Menu.php (register_menu()).
  5. Open Theme Settings in wp-admin (admin.php?page=theme-settings&section=…).

Customize

  • Navigation: add_section / add_sub_section — §2.
  • New field types: Singleton + register(), render, sanitize, and (when adding a type) document sto_render_section_content priority — §5 and README.md.
  • Styling: Scoped under .sto-option-panel-wrapper — see plugin assets/admin/css.

1. Overview

Theme Settings is one admin page. Each navigable panel is a leaf (section query arg). Fields register with section_slug equal to that leaf.

Golden rule Match 'section_slug' on every field to a leaf slug from your sidebar tree. First call Menu::register() for the WP admin page, then add_section / add_sub_section (§1.1, §2). To add fields: create includes/Admin/Sample/Fields/{Name}/{Name}.php with a singleton class (filename = class name, PascalCase). In init(), boot any field-type singletons you need, then call register() / register_many(). You do not need add_action( 'sto_include_option_fields', … ) for ordinary lists — the plugin queues early register() calls until that hook (FieldRegistrationDeferral).

Theme Settings wiring has three steps on SimpleThemeOptions\Admin\Options\Menu. Do them in order — they are not interchangeable.

  1. WP admin menu — $menu->register( $title, $page_slug, $icon ) creates the top-level screen. URL: admin.php?page={page_slug} (e.g. my-settings). Theme/client menus do not pass a demo flag — the plugin sample registers first and owns demo capability.
  2. Sidebar tree — $menu->add_section() and $menu->add_sub_section() build the in-page left nav and the ?section= query arg. This is separate from step 1.
  3. Fields — Select::register(), Group::register(), etc. Each row needs 'section_slug' => '{leaf}' matching a leaf from step 2 (usually a subsection slug).

  • dashicons-* in the STO sidebar — use Font Awesome classes (fa-light fa-…).

WooCommerce Product data (per-product fields)

Some themes show extra STO fields inside WooCommerce’s Product data box when you edit a product. Each product has its own values — they are not the same as global Theme Settings.

If you use the Battery BD theme, open Battery Specifications or Product Tabs in Product data. Field labels come from the theme; this section explains how to fill them in and how developers read them in templates.

How to edit (admin)
  1. In wp-admin go to Products and open a product (or add a new one).
  2. Scroll to the Product data box (same area as General, Inventory, Shipping).
  3. Click your theme’s tab — e.g. Battery Specifications or Product Tabs.
  4. Fill in the fields (text, numbers, switchers, specification rows, custom tabs with classic editor content, etc.).
  5. Click Update or Publish on the product — there is no separate STO Save button. Values save with the product.
Tip Conditional fields (e.g. only on “New” vs “Service”) show or hide when you change the tab switcher at the top of the panel — same behaviour as Theme Settings required rules.
Read values in your theme

Each field has an id (chosen when the theme registers fields). On the storefront, pass the product post ID and that id to sto_get_post_option():

if ( ! function_exists( 'sto_get_post_option' ) ) {
	return;
}

$product_id = (int) get_the_ID(); // single product page

// Text (Battery BD example id)
$capacity = sto_get_post_option( 'bbd_spec_battery_capacity', $product_id, '' );

// Number
$cells = (int) sto_get_post_option( 'bbd_spec_battery_cell', $product_id, 0 );

sto_get_option() and sto_option_is_on() read global Theme Settings only. For product fields always use sto_get_post_option( $id, $product_id, $default ).

sto_get_option()

Returns one saved field by its registered id. Values live in the flat map sto_options[ 'field_id' ] — like Redux get( 'opt_name', 'field_key' ), but you only pass the field key. If the key is missing, your $default is returned.

if ( function_exists( 'sto_get_option' ) ) {
	$heading = sto_get_option( 'hero_heading', 'Welcome' );
}

sto_get_post_option()

Returns one field saved on a specific post (post editor metabox or WooCommerce Product data tab). Reads only _sto_theme_settings_post — it does not merge global sto_options. Use on single product templates with the product ID.

if ( function_exists( 'sto_get_post_option' ) ) {
	$product_id = (int) get_the_ID();
	// Battery BD example ids — use your theme’s field `id` values.
	$capacity   = sto_get_post_option( 'bbd_spec_battery_capacity', $product_id, '' );
	$cells      = (int) sto_get_post_option( 'bbd_spec_battery_cell', $product_id, 0 );
}

Per-product fields on WooCommerce edit screen: §2.1d · Read in your theme. Battery BD ids: bbd_spec_* (see table in §2.1d).

sto_option_is_on()

Use for Switcher and checkbox-style fields. Returns true when the stored value is 1, true, on, or yes.

if ( function_exists( 'sto_option_is_on' ) && sto_option_is_on( 'show_promo_bar', false ) ) {
	// render promo bar
}

Color → inline CSS

Turn a stored Color value into a safe background-color fragment (rgb() / rgba()). Use with esc_attr() in your markup.

  • sto_color_field_background_css( 'field_id', '#ffffff' ) — reads the option for you.
  • sto_color_string_to_background_css( $stored, '#ffffff' ) — when you already have the raw string.
$bg = sto_color_field_background_css( 'header_bg', '#ffffff' );
echo '<div style="background-color: ' . esc_attr( $bg ) . ';">';

Admin saves alpha colors as #RRGGBBAA when data-alpha-color-type="octohex" is set (default vendor hex drops the alpha channel).

Responsive fields

When a field uses 'responsive' => true, sto_get_option() returns a breakpoint map (not a single scalar). Pick one viewport with sto_get_responsive_option() — see §3 Responsive.

$size = sto_get_responsive_option( 'heading_scale', 1200, 'm' );

Advanced: full maps via sto_get_options(), post overrides via sto_get_effective_options_for_post(), term overrides via sto_get_effective_options_for_term() — see README.md.

Safety guard

Wrap calls when the theme must still load if Topten Simple Theme Options is deactivated.

if ( function_exists( 'sto_get_option' ) ) {
	$value = sto_get_option( 'your_field_id', 'fallback' );
} else {
	$value = 'fallback';
}

3. Responsive — how it works

3.1 Turning responsive on

Add 'responsive' => true (or a non-empty array — array only opts in; use 'device' for the tab list). Storage becomes a map of breakpoint => value under the same option id.

3.2 Default device tabs

If you omit device, the admin shows the default trio: xxl (desktop), md (tablet), mobile. If you pass 'device' => array( 'lg', 'md' ), the UI merges with the default set (deduped, canonical order).

3.3 HTML name attributes (scalar example)

Non-responsive select: name="sto_options[my_setting]". Responsive select: name="sto_options[my_setting][xxl]", [md], [mobile] (only keys for shown tabs).

3.4 Conditional required uses the eval breakpoint, not the visible tab

Each responsive row gets data-sto-require-eval-bp (default xxl). JS getOptionFieldValue( key, '' ) and PHP RequiredVisibility read that slice so show/hide does not flicker when you switch device tabs.

Defaults

Per inner field per panel id.

On first install, missing keys fall back to your default until the user saves the leaf. After save, only posted keys for the active leaf are updated; other leaves keep their stored values.

Conditional visibility (required)

Supported.

Rules are stored as JSON on the row (data-sto-required). AND inside one object; OR across an array of objects. Visibility uses the same logic in PHP and JS so admin and save agree.

Responsive storage

On inner fields.

Enable with 'responsive' => true. Optional 'device' => array( 'xxl', 'md', 'mobile' ) (merged with defaults). HTML names become sto_options[id][xxl], etc. Conditional required reads the eval breakpoint (xxl by default), not necessarily the tab you are viewing.
